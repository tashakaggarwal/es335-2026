Architecture & Validation

Pipeline & Methodology

End-to-End Modeling Pipeline

  1. Ball-by-ball parsing. Cricsheet JSON files are aggregated into one row per completed over of each regular second innings: score, wickets, balls remaining, run rates, and recent boundaries.
  2. Temporal split by season. Seasons 2008–2023 form the training set, 2024 is used for model selection, and 2025–2026 are held back for a single final test evaluation.
  3. Feature engineering. Empirical DLS exponential resource curves and par-score differences fitted on training first innings, venue/rolling par targets, phase indicators, settled-batter interactions, dugout batting depth, remaining bowling attack economy, venue chase records, home edge, and 5-match team form.
  4. Baseline benchmarks. Evaluated against a constant training win rate, an over-by-over empirical rate, and the run-rate rule (current rate at least required rate).
  5. Grouped cross-validation & recency weights. Logistic regression, histogram gradient-boosted trees, and an MLP tuned via 5-fold GroupKFold (grouped by match ID) with exponential recency weighting across seasons.
  6. Single-shot test evaluation. The simplest candidate within 0.003 validation log loss of the best was refitted on 2008–2024 and evaluated once on 2025–2026.

Data Leakage Controls

Chronological splits
Every match stays wholly in a single split, and models are only evaluated on seasons played strictly after the training window.
Strictly past-only history features
Batter strike rates, venue chase rates, home records, and team form use only matches strictly before the match date, verified against a brute-force recomputation.
In-fold preprocessing
Median imputation and standard scaling are fitted inside each cross-validation fold pipeline to prevent fold leakage.
Locked test evaluation
The test notebook writes a lock file after one execution so test metrics are never used to iterate on features or hyperparameters.
